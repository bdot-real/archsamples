Architecture · The core guarantee

The Zero-Knowledge Guarantee

The central claim is zero-knowledge-by-policy: the operator — a human running the console, or anyone who compromises an operator session — can manage credential requests but can never read the credentials a recipient submits. This is the property everything else in the architecture exists to protect.

The claim, precisely

No operator-scoped identity has any Vault capability that permits reading its tenant's sepulchre/data/<tenant>/inbound/*. Submitted credentials live only there. The single identity class allowed to read them is a service account authenticating with an AppRole token.

Three independent layers

The guarantee is not one control; it is three, each sufficient to embarrass an attacker who defeats the others.

LAYER 1

Policy

Operator identities carry an explicit deny on the tenant inbound path. Vault evaluates deny before allow; no policy stacking, token wrapping, or capability union can override it. The policy is published and diffable.

LAYER 2

Code

The broker has no function that reads an inbound secret into a log, response, or queue. A CI semgrep gate fails any PR that introduces a path from a Vault-read value to a sink. Sensitive routes use distinct types from metadata routes.

LAYER 3

Operational

No human shell access to production; policy-touching changes need two-person approval; secret-adjacent columns are filtered from interactive DB sessions; continuous attestation alerts on any inbound read by a non-service identity.

The published artifact

The proof is not a paragraph of prose — it is a policy file you can read and diff. operator.hcl.tmpl is rendered per tenant ({{TENANT}} → tenant id) and written to Vault as operator-<tenant>:

# ── Inbound: operator sees metadata, NEVER the secret data (per tenant) ──
path "sepulchre/data/{{TENANT}}/inbound/*" {
  capabilities = ["deny"]
}
path "sepulchre/metadata/{{TENANT}}/inbound/*" {
  capabilities = ["list", "read"]
}

Two things make this airtight in Vault:

  1. deny is explicit, not merely absent. The operator can list intake metadata so the console can show "fulfilled / pending" — but the secret data path carries an explicit deny.
  2. Vault evaluates deny before allow. Even if a future policy mistakenly granted read on the same path, the deny still wins.

Because the secret never enters Postgres (metadata only — schema note N-007) and never enters a log (issue #15), the Vault policy is the only gate that matters, and it is shut.

Verifying it yourself

A published policy is worthless if the running Vault enforces something looser. tools/verify-policy.sh closes that gap — it reads the live policy and proves the operator is actually denied. Two independent checks:

CheckWhat it doesFails when
Policy diffReads vault policy read operator-<tenant> from the live cluster, normalizes whitespace/comments, diffs against the rendered template.Any drift → exit 1 with a diff.
Behavioral assertionMints a real operator-scoped token and attempts vault kv get sepulchre/<tenant>/inbound/probe.If that read succeeds, zero-knowledge is broken → exit non-zero. The guarantee is proven by the read being denied, not by reading the policy text.
 
# From the repo root, with the dev stack provisioned:
bash tools/verify-policy.sh

# Expected:
OK: live policy matches the published artifact (tenant t_default)
OK: operator-t_default denied on sepulchre/data/t_default/inbound/* (zero-knowledge holds)
==> zero-knowledge property verified for tenant 't_default'.
Watch it fail

A guard you have only ever seen pass is not a guard you trust. Grant the operator a read capability on the inbound path and the script rejects it — FAIL + diff, exit 1. Restore by re-running vault/provision.sh, which re-renders and re-writes the per-tenant policies.

Enforced continuously in CI

This isn't a one-time demo. The zero-knowledge-proof job in .gitea/workflows/ci.yml runs on every push and pull request: it stands up an ephemeral Vault, provisions it from the published policies, runs verify-policy.sh, and then deliberately tampers the live policy to confirm the guard still bites. A change that loosens the operator policy — anywhere in the repo — fails the build.

The strongest form — BYOK

When a tenant supplies their own KMS seal key, revoking it makes their data cryptographically inaccessible including to the Sepulchre operator. The POC ships the policy-layer guarantee above; BYOK is v0.2. See Audit & Crypto for the key hierarchy.
