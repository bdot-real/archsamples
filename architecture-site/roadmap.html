Architecture · Tenancy, Lifecycle & Roadmap

Tenancy, Lifecycle & Roadmap

How Sepulchre scales from one box to many tenants, what happens to a credential after it's submitted, and the sequenced plan for runtime retrieval and on-box AI — all constrained by two invariants: the operator stays blind, and AI never sees plaintext.

Tenancy model — two shapes, one codebase

Pooled multi-tenant default SaaS

One Vault cluster with path-prefix isolation per tenant and policy templating; shared Postgres with row-level security keyed on tenant_id (every table, every query, enforced at the DB layer); a shared broker fleet with tenant context threaded through every call and bound to the request token.

Siloed single-tenant regulated

Dedicated Vault cluster, dedicated Postgres, dedicated broker replicas per tenant; the tenant supplies their own root of trust (BYOK or HSM); can run entirely in the tenant's own infrastructure.

Selection is a deployment-module choice, not a feature flag in code. The same application binary runs both shapes.

Credential lifecycle — standing → rotation → leased

What happens to a submitted credential after its intake is fulfilled.

Standing (the default, N-051)

A fulfilled intake is standing: the value is retained in Vault and readable by a bound reader at any time through the audited service path. CI jobs and containers fetch the same credential across many runs, so it must persist. The operator still can never read it — persistence changes nothing about zero-knowledge.

Rotation (re-submission)

When the underlying secret changes at its source, the operator rotates the intake instead of creating a new one — the id, name, fields, and allowed_readers are preserved, so every bound reader keeps working without reconfiguration.

POST /api/v1/intakes/:id/rotate        (operator session)
  → issues a fresh submission token, status back to `pending`, version += 1
  → emails the recipient a new submission link
  → returns { id, intake_url, expires_at, version }

Readers learn of a change through the version / rotated_at fields returned on every read — a reader that caches compares version and re-fetches when it increases, so no prior value is ever exposed to detect the change. Machine readers also get an auditable reader.notify hook (wired to a webhook / SIEM / chatops) alongside the intake.rotate event.

Availability note

While a rotation is mid-flight (re-opened, not yet re-submitted) the service read returns 404 — the new value isn't in yet and the old one is being replaced. Rotate during a maintenance window, or (future work) serve the prior KV version until the new one lands.

Future: dynamic / leased secrets (sketch)

The next step is credentials Sepulchre mints on demand with a TTL, so there is nothing standing to steal: back an intake with a Vault dynamic-secrets engine (database, AWS STS, PKI); the service read returns a lease (value + lease_id + TTL) instead of a stored value; revocation becomes immediate and per-lease. The version / rotated_at fields and the reader.notify hook are the forward-compatible seams leased credentials will reuse.

The embedded AI substrate

AI features (audit Q&A, compliance narratives, semantic search, MCP agent access) run on an on-box, in-process model — because a hosted API would ship tenant audit metadata to a third party, contradicting the zero-knowledge posture. The load-bearing constraint (#66) is that the model never sees plaintext and audit metadata never leaves the box.

Why constrained output, not text-to-SQL

At tiny sizes a model can't be trusted to author safe SQL, and free-form SQL is an injection and exfiltration surface even on metadata. The model is grammar-constrained to emit only the small query-object schema the audit endpoint already supports — invalid or out-of-vocabulary output is structurally impossible. The decision is captured as code in packages/ai/src/substrate.ts.

Sequenced roadmap

The throughline: runtime retrieval and the agentic part of AI share one backbone — scoped machine/agent identities reading through an audited, policy-gated path — and UI trails the capabilities it surfaces (except the design system, which runs in parallel from day one).

  • PHASE −1

    Multi-tenancy now, not later

    Pulled forward from v0.2 because tenant-safe isolation is a prerequisite, not a retrofit: tenant model + provisioning, Postgres RLS, per-tenant Vault paths + templated policies, tenant resolution/routing, per-tenant operator auth, tenant-aware audit, a cross-tenant isolation test suite, an onboarding CLI (#44–#51).

  • PHASE 0

    Keystone — per-credential reader binding

    The single most important addition; it unblocks runtime and agentic use. Add allowed_readers to the intake model (bound to Vault entities / OIDC claims / AppRole roles), enforced at both the Vault policy layer and a broker check, with reader provenance in every audit event.

  • PHASE 1

    Runtime retrieval (the backbone)

    OIDC / workload auth: a CI job exchanges its ephemeral OIDC token for a short-lived Vault token — no stored secret_id (solves "secret-zero"). Clients: a Gitea/GitHub Action, a CLI (#29, shipped), a language SDK (#30), and a Vault Agent sidecar pattern for containers. Every read is audited with provenance; the operator stays blind.

  • PHASE 2

    AI on the metadata plane scope: 2c + 2e

    Audit Q&A + compliance narratives (#67–#69) on the embedded substrate; an MCP server exposing "request a credential" as an agent tool (#70–#71) — an agent is just a scoped, audited reader, and a human approves. Cross-cutting guardrail #66: "AI never sees plaintext," enforced by the semgrep gate.

  • PHASE 3

    UI — visual refresh in parallel; feature-surfacing trails

    Promote @sepulchre/ui from CSS tokens to a real component + token system (branding, light/dark, accessibility) — starts day one, no dependency, keeps the strict CSP intact. Then surface reader-binding and runtime reads in the audit timeline, and the AI features as they land.
