Architecture · Data Flows

The Two Canonical Flows

Everything Sepulchre does reduces to two motions: a secret coming in that the operator must never see, and a secret going out that may be revealed exactly once. Each is drawn below with the components it touches, the Vault path it lands on, and the policy that guards it.

↓ Inbound — collect a secret the operator can't see

The operator asks a recipient for credentials. The recipient submits them through a one-time intake link straight into Vault. The submitted value never returns to the operator, never touches Postgres, and never lands in a log.

  • Request. The operator creates an intake in the console — naming the recipient and the fields to collect. The broker mints a scoped submission token (HS256 JWT bound to one intake id + jti, short TTL) and returns a copyable intake link. The POC mailer only logs that a notification would be sent — the link itself is in the create response, never a log.
  • Submit. The recipient opens the link on the intake portal and posts values to POST /api/v1/inbox/:id. The broker writes them to Vault KV. The body is never logged at any layer; the broker's request log emits the templated route only.
  • Blind. Nothing in the console ever shows the submitted values, and an operator-scoped Vault token is denied on the inbound data path — provable at any time with verify-policy.sh.
  • Consume. A bound service account (AppRole token) calls the one inbound-read endpoint. The broker performs the read as the caller's token (kvReadAs) — Vault, not the broker, authorizes it — and records intake.read with actor_type: service.
Standing by default

A fulfilled intake is standing: the value persists in Vault and a bound reader can fetch it across many runs (CI jobs, containers). Rotation re-opens the same intake with a fresh token and bumps version, so bound readers keep working without reconfiguration. See the credential lifecycle.

↑ Outbound — share a secret, reveal it once

The operator sends a secret to a recipient one-time. Vault response wrapping does the work: the wrap token reveals nothing about the underlying secret, unwrap is single-use, and a second attempt is a signal that someone else read it.

  • Create. The operator posts a value, a max-view count, a TTL, and optionally a sender-set passphrase to POST /api/v1/shares. The broker writes it to Vault, response-wraps it, and returns a reveal link keyed by the accessor.
  • Notify. The recipient receives the reveal link (out of band in the POC).
  • Reveal. The recipient opens the reveal page and hits GET|POST /api/v1/reveal/:token. If a passphrase was set (argon2id), it's verified as a second factor. The broker unwraps the secret and streams it once, over TLS.
  • Destroy. When the last allowed view is spent, the underlying Vault entry is deleted. The reveal endpoint is rate-limited (10/IP/min) and the link is short-TTL.
Interception is detectable, not silent

Open a spent reveal link again and you get the same generic "unavailable" response — and the audit log records share.reveal with result: denied, reason: exceeded, possible_interception: true. A legitimate recipient who finds their link already consumed learns their channel was compromised. The runbook covers the response procedure.

Why the broker can't cheat on either flow

Both flows route through the broker, so it's the natural place to worry about. The design removes the worry structurally rather than by trust:

  • → Inbound reads run as the caller's token. The broker has no standing inbound-read capability; an attacker who owns the broker host still has no service token, so Vault denies them.
  • → Secret-bearing routes are excluded from logging at the proxy and the app — the broker's structured log emits templated routes only, never the raw path (which carries a capability token) or the body.
  • → A CI semgrep gate fails the build if any code path pipes a Vault-read value or a request body into a logger; a runtime backstop (MetadataLeakError) throws before any audit sink sees a forbidden key.
