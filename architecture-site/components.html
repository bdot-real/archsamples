Architecture · Components

Components & Layers

Sepulchre is deliberately layered so that each component has one job and a short list of things it is structurally unable to do. The zero-knowledge property is not one component's responsibility — it is what remains true because no single component can violate it.

Logical layers

Component responsibilities

Edge surfaces Astro · static bundles

Four presentation surfaces, built and served independently so a compromise of one cannot reach another's DOM. The intake portal (:4321) and reveal page (:4322) ship the strictest CSP of any surface — no third-party scripts, no analytics, no externally-loaded fonts, minimal JS. The operator console (:4323) is a normal SPA. A CLI (@sepulchre/sdk) and an MCP server drive the same broker API from a terminal or an agent.

Cannot: the credential surfaces load no code that could exfiltrate a keystroke; the console is a separate origin/bundle from the intake DOM.

Edge proxy Traefik v3

TLS 1.3 termination, HSTS, rate limiting, and request shaping. It classifies routes into two kinds: secret-bearing (POST /api/v1/inbox/:id, POST /api/v1/shares, GET|POST /api/v1/reveal/:token) where request/response bodies and headers are never logged, and metadata routes where normal logging applies. The distinction is configured at the proxy — see traefik/dynamic/security.yml — not left to the application. Referrer-Policy: no-referrer keeps URL-embedded capability tokens out of the Referer header.

Cannot: emit a secret-bearing body or an Authorization/Cookie/X-Vault-Token header into an access log.

Broker service Hono · stateless

The workflow core. It holds connections to Vault and Postgres and handles auth, tenant lookup, policy decisions, Vault calls, audit emission, and notifications. It is stateless — multiple replicas sit behind the proxy, and readiness is separated from liveness so rolling deploys don't drop a wrap-token unwrap mid-flight. Its source is organised by concern: auth/, intake/, share/, tenant/, vault/, audit/, plus byok.ts and cse.ts for the seal/client-side-encryption seams.

Cannot: read an inbound secret with a capability of its own. The single inbound-read endpoint reads as the caller's service-account token (kvReadAs) — Vault, not the broker, is the authority. A CI semgrep gate fails any code path from a Vault-read value to a logger, response body, or queue.

Vault KV v2 · Transit · response-wrap

The cryptographic core and the sole home of secret values. Per tenant: a KV v2 mount for stored inbound secrets, a Transit mount for client-side encryption and key derivation, and response wrapping for one-time outbound shares. An audit device streams every operation. Tenant isolation on OSS Vault uses path prefixes plus policy templating (operator.hcl.tmpl, service-account.hcl.tmpl, intake-token.hcl.tmpl) — operationally equivalent to Enterprise namespaces for this use case.

Cannot: be overridden by policy stacking — Vault evaluates deny before allow, so the operator's explicit deny on the inbound path always wins.

PostgreSQL metadata only · via PgBouncer

Holds tenants, users, tenant config, intake and share metadata (recipient hashed identifier, expiry, view count, status, version), an audit mirror for fast console queries, and OIDC identity links. It never contains a secret value and never contains anything that decrypts one. Row-level security keyed on tenant_id enforces tenant isolation in pooled deployments; PgBouncer pools connections in transaction mode; WAL is archived continuously to object storage for PITR. No vendor-specific features — vanilla Postgres 16.

Cannot: yield a secret to an attacker who compromises it — there is nothing secret to yield (schema note N-007).

Audit pipeline signed · tamper-evident · WORM

Every operation produces an audit event. Each event embeds the SHA-256 of the previous one (a hash chain) and is HMAC-signed under a per-tenant key, then fanned out to: Postgres (fast console queries), a signed JSONL file, a WORM object-store archive (S3-API + Object Lock, compliance mode — undeletable even by root until retention expires), and a tenant SIEM via syslog/webhook with buffered retry so no event is dropped. The chain fails closed on any post-hoc edit, deletion, reorder, or forgery. Covered in depth on the Audit & Crypto page.

Cannot: accept an event whose metadata carries a forbidden key (password, value, token, …) — the emitter throws MetadataLeakError before any sink sees it.

Embedded AI substrate on-box · metadata-only

An optional, on-box tiny LLM (node-llama-cpp, GGUF, grammar-constrained output) for audit Q&A and compliance narratives, running in a dedicated worker with no Vault credentials at all. It consumes metadata, audit records, and policy documents only. Natural-language questions are mapped to a whitelisted audit-query object — never free-form SQL — which the broker compiles to a parameterized, tenant-scoped query. See the Roadmap.

Cannot: see plaintext. Two semgrep rules (the "AI never sees plaintext" gate, #66) fail the build if a Vault-read value flows into a model call, or if any code under an ai/ path touches the Vault read surface.

Pluggable root of trust seal / auto-unseal

Vault's seal is abstracted behind a configured provider — AWS KMS, GCP KMS, Azure Key Vault, another Vault's Transit engine, a PKCS#11 HSM, or Shamir for air-gapped. Reference seal configs ship in deploy/docker-compose/vault/seal/. Self-hosters stay fully cloud-independent via Transit auto-unseal from a small secondary Vault; enterprise tenants can BYOK on any provider.

Cannot: unseal tenant data if a BYOK tenant revokes their key — that data becomes cryptographically inaccessible, including to the Sepulchre operator.

Repository shape

A pnpm + Turborepo TypeScript monorepo. The split mirrors the layers above:

PathWhat lives there
apps/brokerThe Hono broker — routes, auth, intake/share/tenant logic, Vault client, audit sinks, BYOK & CSE seams, mailer.
apps/portal · reveal · consoleThe three Astro presentation surfaces (intake, one-time reveal, operator console).
apps/mcpMCP server exposing "request a credential" as an agent tool over the audited backbone.
packages/vault-clientTyped Vault client — KV v2, Transit, response-wrap, kvReadAs.
packages/dbDrizzle schema & migrations (metadata only).
packages/auditHash-chain + HMAC signing, sink fan-out, chain verification.
packages/aiThe AI substrate config & boundary (metadata-only, no Vault reach).
packages/sdkThe sepulchre CLI + language SDK, cert-pinned transport.
packages/shared-types · uiCross-package types; the design-system CSS tokens / components.
deploy/docker-compose (dev, prod, HA), Traefik security config, Vault policies & seal configs, backup/restore.
POC vs. target

The running POC is a single box: file-storage Vault, one Postgres, one broker, TypeScript throughout. HA (Vault Raft cluster, Postgres streaming replicas, multi-region DR) and pooled multi-tenant hardening are described here as the target topology — see the Roadmap for what is shipped, in flight, and deferred.
