Architecture · Audit & Cryptography

Audit & Cryptography

The audit log is the product. Zero-knowledge is only credible if you can prove what was and wasn't read — so every operation is signed into a tamper-evident chain, shipped to storage that even root can't erase, and backed by a key hierarchy where the strongest configuration locks out even the Sepulchre operator.

Every operation is an audit event

Each event is a structured record whose metadata never contains a secret value (enforced by the MetadataLeakError backstop). Two fields make the log tamper-evident:

{
  "event_id":   "01HQ…",
  "prev_hash":  "sha256:…",           // links to the previous event
  "timestamp":  "2026-05-25T14:23:11.482Z",
  "tenant_id":  "t_abc",
  "actor": {
    "type":        "service | human | recipient",
    "identity":    "service-deploy@tenant-abc",
    "auth_method": "approle | oidc | wrap-token",
    "ip": "…", "user_agent": "…"
  },
  "action":   "intake.submit | intake.read | share.create | share.reveal | …",
  "resource": "sepulchre/data/t_abc/inbound/sub_xyz",
  "result":   "success | denied | error",
  "metadata": { /* never contains secret values */ },
  "signature": "hmac-sha256:…"        // per-tenant key, in Vault
}

Tamper-evidence: the hash chain

prev_hash embeds the SHA-256 of the previous event, so the log is a chain: edit, delete, insert, or reorder any event and every link after it breaks. The signature is an HMAC-SHA256 under a per-tenant key derived from a broker-held master key that is never in the database — so even the operator can't forge events post-hoc without leaving a detectable gap.

Shipped — #24 complete

pnpm --filter @sepulchre/broker audit:verify walks the chain and fails closed on any post-hoc edit, deletion, insertion, reorder, or forgery. This is not roadmap — it is the current behaviour of the POC.

Immutability: WORM archival + SIEM

A signed event is fanned out to sinks that make it independently verifiable and un-erasable off the box:

Postgres

An audit mirror for the operator console's fast timeline queries. Not the system of record for immutability — the object store is.

WORM object store

S3-API + Object Lock in COMPLIANCE mode: the version cannot be deleted or overwritten, even by root, until the configured retention expires.

SIEM

Shipped to the tenant's SIEM over syslog/webhook with buffered retry — no event is dropped if the sink is briefly unavailable. Per-tenant routing (#28).

Because every off-box copy is signed by the same per-tenant HMAC key and chained, a tenant can verify any copy independently of Sepulchre. The signed JSONL file on disk is a fourth, offline-verifiable copy.

The key hierarchy

Standard Vault at rest, with per-tenant derivation so a compromise or revocation is scoped to one tenant:

LayerHow it works
At restEach KV entry is encrypted with a key derived from the mount's master; the master is encrypted by the seal key from the configured root of trust.
In transitTLS 1.3 everywhere, HSTS, certificate pinning in the CLI/SDK (RFC 7469 SPKI hashes; pin a long-lived CA and rotate leaves freely).
Optional client-side encryptionParanoid tenants can have the intake portal derive a key from Vault Transit (/transit/datakey/wrapped/<tenant>) in the browser, encrypt before submission, and ship only ciphertext. The broker never sees plaintext. (Seam: broker/src/cse.ts.)

Pluggable root of trust

Vault's seal is abstracted, so the entire stack can be cloud-independent or bound to a cloud KMS as the deployment prefers. Reference configs ship in deploy/docker-compose/vault/seal/:

Cloud KMS

awskms.hcl, gcpckms.hcl, azurekeyvault.hcl — auto-unseal from a managed KMS.

HSM & Transit

pkcs11.hcl for a hardware HSM; transit.hcl to auto-unseal from a small secondary Vault (fully self-hosted).

Air-gapped

shamir.hcl — Shamir key shares with sealed envelopes for fully offline operation.

BYOK — the strongest form of the claim

v0.2

A tenant supplies their own KMS key; Vault uses it for seal. If the tenant revokes the key, that tenant's data becomes cryptographically inaccessible — including to the Sepulchre operator. This upgrades the guarantee from "operator is denied by policy" to "operator is denied by mathematics." The POC ships the policy-layer guarantee (see Zero-Knowledge); BYOK is the v0.2 escalation (seam: broker/src/byok.ts).

Why this matters commercially

Compliance buyers pay for evidence, not promises. A per-tenant continuous-attestation report — every identity with potential read access, every actual read with timestamp and identity, signed by the audit hash chain — is a first-class artifact. For a clean tenant, the human-read list is empty and provably so. That provability is the difference between "we don't look at your secrets" and "you can verify we can't."
