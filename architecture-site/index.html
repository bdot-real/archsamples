Architecture · Overview

Sepulchre

A credential broker built on HashiCorp Vault whose defining property is zero-knowledge by policy — the operator's inability to read the credentials a recipient submits is enforced by a Vault deny policy and provable from the audit log, not promised in a privacy statement.

Apache-2.0 TypeScript · Node 22 Hono · Drizzle · PostgreSQL 16 Vault OSS · KV v2 · Transit Astro · Traefik v3 · Docker prod · sepulchre.melx.xyz

Sepulchre solves a narrow, sharp problem: how do you let one party hand a secret to another party through a service you run, without that service — or the humans operating it — ever being able to read the secret? It does this with two flows and one uncompromising guarantee.

The guarantee, in three sentences

Operator-blind inbound

Submitted credentials live only in Vault KV at sepulchre/data/<tenant>/inbound/*. The operator role carries an explicit deny there; only a designated service account (Vault AppRole) can read it.

Never in Postgres or logs

Postgres holds metadata only — no secret values, no tokens, no decryption material. Secret-bearing bodies and capability-token URLs are never written to any log, at any layer.

Proof you can run

The published policy artifact is a file you can diff; tools/verify-policy.sh proves the live Vault enforces exactly it. CI re-proves it — and tampers it — on every push.

Architecture at a glance

Everything above the broker is a thin, separately-built presentation surface; everything below it is boring, replaceable infrastructure. The interesting part is the single line through the middle — the broker is stateless and, by design, cannot itself read an inbound secret. It reads on the caller's behalf, as the caller's token, or not at all.

Two flows

↓ Inbound — collect a secret

The operator requests credentials; the recipient submits them via a one-time intake link straight into Vault. The operator can never read the submitted values — a bound service account can, and every such read is audited.

↑ Outbound — share a secret once

The operator shares a secret one-time; the recipient reveals it once via a Vault response-wrap token. When the last allowed view is spent the underlying entry is destroyed, and a second attempt is flagged as possible interception.

POC scope vs. target state

The running proof-of-concept (v0.1) is single-box, TypeScript, with the zero-knowledge property genuinely enforced and the tamper-evident audit chain (#24) complete. The broader component design describes the target state — HA Vault Raft, Postgres replicas, multi-region, BYOK, pluggable roots of trust.
